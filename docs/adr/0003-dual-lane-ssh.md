# ADR-0003：逻辑会话采用双通道 SSH 调度

- 状态：Accepted
- 日期：2026-08-23
- 影响范围：SSH、SFTP、远程编辑、监控、连接池与性能验收

## 背景

交互终端对尾延迟敏感，而 SFTP、远程编辑和打包传输追求吞吐。把两类工作无条件塞入同一 SSH 连接会受到窗口和拥塞竞争；无条件为每个功能建立连接又会增加认证、服务器负载和 host key 状态复杂度。

## 决策

每个用户可见会话是一个逻辑会话，由 actor 暴露两条调度 lane：交互 lane 承载 shell、窗口尺寸和心跳；批量 lane 承载 SFTP、编辑、校验和大文件任务。

默认在同一 SSH 连接中使用独立 channel，并对批量任务施加并发、窗口和队列限制。能力探测或运行时指标表明交互预算无法满足时，连接管理器可以建立第二条经过完整 host key 与认证流程的 SSH 连接承载批量 lane。

连接数同时受全局、单主机和单逻辑会话上限约束。监控探针属于低优先级控制任务，不得抢占交互 lane。纯 Rust SSH 为主路径，平台 OpenSSH 仅作显式兼容回退。

## 备选方案

| 方案 | 复杂度 | 交互延迟 | 资源成本 | 结论 |
| --- | --- | --- | --- | --- |
| 所有任务单连接无调度 | 低 | 高负载下不可控 | 低 | 拒绝 |
| 每项功能固定独立连接 | 中 | 好 | 认证和服务器成本过高 | 拒绝 |
| 双 lane，按指标升级第二连接 | 中到高 | 可控 | 按需增加 | 采用 |
| 全部委托外部 OpenSSH 进程 | 中 | 可控性有限 | 进程和平台差异大 | 仅回退 |

## 结果

正面结果是产品可以同时追求终端低延迟和文件高吞吐，并能在服务器限制下自适应。代价是会话状态机、连接配额、重连和测试矩阵更复杂。

M0 必须用真实 SSH 服务器验证 channel 公平性和第二连接切换；M3 以“10 个活跃终端加 2 个传输”及 OpenSSH SFTP 基线作为验收证据。若 russh 无法满足关键能力，应记录具体缺口后启用受限回退，而不是静默改变安全策略。
